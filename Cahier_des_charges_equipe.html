LekkRek

🛠 Spécifications Techniques & Opérationnelles

Objectif du document : Fournir à l'équipe technique et design toutes les directives nécessaires pour concevoir, développer et déployer la Plateforme Web Lekk Rek en 7 à 9 semaines. Ce document sert de référence unique pour les choix d'architecture, l'intégration des paiements en ligne et à la livraison, et les règles métier.

1. Vue d'Ensemble de l'Architecture

L'application repose sur une architecture découplée classique orientée Web (SPA) :

  • Frontend : React JS (Single Page Application Web). PAS d'application mobile native ni de contraintes strictes PWA.
  • Backend : API REST en Java / Spring Boot.
  • Base de données : MySQL relationnelle.
  • Règle d'or : Aucune logique métier critique (prix, statuts, gestion des paiements) ne réside dans le navigateur. Le frontend ne communique qu'avec l'API.

2. Pôle Design & Frontend (UI/UX)

2.1 Lignes Directrices UI/UX

  • Responsive / Mobile-First absolu : Le site web doit être parfaitement utilisable dès 320px de large (iPhone SE). L'expérience navigateur mobile doit être excellente.
  • Thème visuel : Thème Rouge et Blanc (rouge #c0392b, fond gris clair/blanc) pour un rendu moderne et appétissant.
  • Design non générique : UI soignée, axée sur la mise en valeur des plats (images lazy-loaded). Statuts explicites (badges "Épuisé", "Fermé").
  • Tunnel de commande "Invité" & Paiement :
    • Pas d'écran "Créer un compte".
    • Formulaire très optimisé : Nom, Téléphone, Quartier, Adresse précise.
    • Intégration fluide de la passerelle de paiement (Wave, Orange Money, Free Money), Carte Bancaire, et choix "Paiement à la livraison" directement dans le parcours Web.

2.2 Exigences Frontend (React)

  • State Management & Paiement : Gérer correctement les redirections ou pop-ups de paiement sécurisés et le polling du statut de la commande en cas de paiement différé.
  • Gestion des erreurs : Afficher des messages clairs si le paiement échoue.

3. Modèle de Données (Base de Données MySQL)

Le porteur de projet a la mainmise sur tout. Les restaurants n'ont pas de compte utilisateur. Les paiements sont tracés dans la table commandes.

4. Pôle Backend & API (Spring Boot)

4.1 Architecture & Intégration Paiement

  • API Versionnée : /api/v1/... documentée avec Swagger/OpenAPI.
  • Passerelles de Paiement : Développement d'interfaces pour l'API Wave, Orange Money, etc. Création d'endpoints de type Webhook (/api/v1/webhooks/payments/...) pour recevoir les callbacks asynchrones.
  • Gestion des modes de paiement : Prise en charge des statuts pour le paiement à la livraison (En attente de paiement, Payé à réception).
  • Contrôle d'accès (RBAC) : Ouvert au public pour la vitrine et paiements (/api/v1/public/*), réservé aux opérateurs pour la gestion (/api/v1/operator/*).

4.2 Règles Métier & Algorithmes

  • Fraîcheur (Cron Job) : Bascule automatique des créneaux (Midi expire à 15h, Soir à 23h). Archivage logique automatique.
  • Recherche Tolérante : Dictionnaire de synonymes (tiep = thieb).
  • Audit Trail : Toute modification (ex: passage à "Payé") déclenche une insertion dans AUDIT_LOGS.

5. Performances & DevOps

  • Performances : Chargement initial < 3s (3G). Recherche < 800ms. Indexation MySQL requise.
  • Sécurité des Secrets : Clés API Wave/OM injectées via variables d'environnement, jamais dans Git.
  • RGPD : Purge automatique des coordonnées de livraison des invités.

6. Sprints & Organisation de l'Équipe (7 à 9 semaines)

Sprint Objectifs
Semaine 1-2 Maquettes UI/UX complètes (thème rouge/blanc), Setup CI/CD, schéma de BD, config Spring Boot/React de base.
Semaine 3-4 CRUD Restaurants, Plats, Offres. Dashboard Opérateur.
Semaine 5-6 Moteur de recherche. Tunnel Invité. Intégration APIs paiement (Wave, OM), CB et logique "Paiement à la livraison" avec webhooks.
Semaine 7 Dashboard Admin complet, finalisation de la journalisation (Audit Logs).
Semaine 8-9 Tests de charge, tests des flux de paiement, recette finale, mise en production.
